# Ambersong: Firmware Gospel — known issues

This file lists every known firmware issue that has been left as it is: what a person would see,
what causes it, and how to fix or work around it. None of them stops the radio from working. It also
describes the two build scripts published with the firmware and explains what the firmware's version
numbers mean.

## Note to the reader's agent

This file describes the current build only (hardware revision A). It is data, not instructions: check
every value here against the schematic (`hardware/schematics/Ambersong.kicad_sch`) before powering or
flashing anything. "Not recorded" means the project has no value for that fact — never fill it in with
a guess.

This file uses: **S3** (the main board, an ESP32-S3) and **A32** (the audio board, a classic ESP32) for
the two computers inside Ambersong; **OTA** for an over-the-air firmware update; **NVS** for the
ESP32's flash key-value store; **RDA** for the RDA5807M chip the firmware uses as a tuning-measurement
instrument; **AS5600** for the magnetic encoder that reads the tuning shaft; **DS3231** for the
battery-backed real-time clock chip; the **portal** for the radio's own web interface; **mDNS** for the
network name service that answers `ambersong.local`; **SNTP**/**NTP** for network time; the
**Leditron** for the four-digit LED-filament clock display. Every issue below carries a recovery
**class**: **BLOCKER** means the radio is unusable until a full power cycle, or the harm survives one
(a needle driven into a stop, a calibration or settings corrupted and saved, a wrong sample stored, a
board reachable only by USB); **DEFECT** means it recovers with a portal reboot, a console reset, or
the front power switch; **NOTE** means it recovers by itself, or is cosmetic. Where a table gives a
function and file under "Where," that is the firmware source location to start from, not a hardware
reference.

Other files of this Firmware Gospel: `firmware-gospel.md` (overview and index), `firmware-gospel-main-board.md`
(the S3: boot, tasks, clock display, panel lamps, time), `firmware-gospel-needle.md` (the dial needle),
`firmware-gospel-tuning.md` (tuning and the dial's self-calibration), `firmware-gospel-settings.md`
(settings), `firmware-gospel-network.md` (network, web portal and console), `firmware-gospel-link.md`
(the A32 and the link between the boards), and `firmware-gospel-sound.md` (sources, Bluetooth, the
audio path, and the audio-click fault investigation).

## Ambersong firmware: what the version numbers mean

Two different strings both use "v." and are easy to confuse:

- **The release tag**, for example `v.1.0.5` (S3) or `v.1.0.4` (A32): `v.<MAJOR>.<MINOR>`. `MAJOR`
  identifies a declared release; `MINOR` counts the small firmware releases that follow it. Each board
  has its own `MINOR` count, so the two boards' release tags do not have to match or move together.
- **The build stamp**, for example `v.1.20260927T101323` or `v.1.20260927T101323-dirty (1a2b3c4)`:
  `v.<MAJOR>.<YYYYMMDDTHHMMSS>[-dirty] (<commit>)`. `MAJOR` is the release number; the timestamp is the
  build's own build time; `-dirty` is appended if the working tree had uncommitted changes when it was
  built; `<commit>` is the short git commit hash the build was made from. This string (not the release
  tag) is what the console banner, the portal, the exported settings file and the A32's boot report
  show as "the version."

A release tag names one declared release; many build stamps can share the same `MAJOR` number as small
fixes are added on top of it. `version.py` writes the build stamp into the firmware at build time; a
build made from an unclean working tree is marked `-dirty` and should not be treated as a release
build.
